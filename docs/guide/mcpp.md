# Six Platforms with mcpp

One manifest, one tool, six platforms: Linux, Windows, macOS, iOS, Android and the Web.
This page is the short path for three kinds of work — an application, a library for the HuxerUI ecosystem, and the SDK itself — from environment to distribution.
[`mcpp/README.md`](../../mcpp/README.md) has the details and [the design record](../design/mcpp-build-system.md) the reasons and the known gaps.

## Environment

One tool. [xlings](https://github.com/d2learn/xlings) installs [mcpp](https://github.com/mcpp-community/mcpp); mcpp installs everything else on first use: compilers, the GTK stack on Linux, the NDK, emsdk, the JDK, simulator tools, packaging tools.

```bash
xlings install mcpp -y --use
mcpp --version            # 2026.9.13.1 or newer
```

iOS additionally needs Xcode on a Mac, because Apple's SDK is located rather than installed.
Nothing else is required on `PATH`; `mcpp self doctor` says what is missing.

## An application

```bash
huxerui create app hello --build mcpp    # or: mcpp new hello --template huxerui.huxerui
cd hello
mcpp build && mcpp run                    # this host
mcpp test                                 # tests/**/*.cpp, one program each
```

The project is a manifest, a one-line build program and module units. No headers, no platform shells:

```
hello/
  mcpp.toml        huxerui.huxerui = "…", platforms = [linux, windows, macos, ios, android, emscripten]
  build.mcpp       huxerui::rules::configure({.resources = "resources"})
  src/main.cpp     the entry, outside the module graph
  src/app.cppm     export module app; import std; import huxerui; import app.resources;
  resources/       raw/, images/ … reachable as app::resources::…
```

`[[huxerui::composable]]`, `View` and `UseState` are the same API as under CMake; `import app.resources;` is generated by hrc from `resources/`.

Another platform is another row of the same manifest:

```bash
mcpp build --target wasm32-emscripten
mcpp build --target x86_64-linux-android
mcpp build --target aarch64-ios-sim         # on macOS
```

What a user installs is `mcpp pack`:

| Row | `--target` | `--format` | `mcpp run --format` hands it to |
|---|---|---|---|
| Windows | `x86_64-windows-msvc` | `msi` | — |
| Linux | `x86_64-linux-gnu` | `appimage` | — |
| macOS | `aarch64-macos` | `app` | — |
| iOS simulator | `aarch64-ios-sim` | `app` | `simctl-run` |
| Android | `x86_64-linux-android`, `aarch64-linux-android` | `apk` | `adb-run` |
| Web | `wasm32-emscripten` | `web` | any static HTTP server |

```bash
mcpp pack --target aarch64-linux-android --format apk
adb install -r target/.build-mcpp/out/hello.apk      # or: mcpp run --target aarch64-linux-android --format apk
```

The APK is debug-signed and carries a launcher icon (the application's `android/res`, or the SDK's); the Web directory serves from any static server.
The SDK CLI speaks the same language for an mcpp project: `huxerui build android`, `huxerui run android` and `huxerui package windows` run the commands above, and `huxerui platform add web` adds the row to the manifest.

## A library for the ecosystem

[Lib-Live2D](https://github.com/HuxerUI/Lib-Live2D) is the worked example: a Live2D model on every row through one dependency line, and nothing about Cubism in the application.

```
live2d/
  mcpp.toml            [package] name = "live2d", namespace = "huxerui", platforms = […]
                       [dependencies] huxerui.huxerui = { git = "…", rev = "…" }
                       [lib] path = "modules/live2d.cppm"
  build.mcpp           huxerui::rules::configure({…}) selects the sources; mcpp::deploy() ships the shaders
  modules/live2d.cppm  export module huxerui.live2d; import huxerui;
  mcpp/cubism/         a path package wrapping the vendor SDK, one xim payload per platform
  examples/preview/    an application that imports the library: its own smoke test on every row
```

Three habits keep a library simple.
It calls the same `configure()` an application does and lets the rule select its sources.
It declares per-platform payloads in `[target.'cfg(…)'.xlings.workspace]` and reaches them with `mcpp::xpkg_dir`.
It deploys only what the application would not: `mcpp::deploy` reaches the consumer's staged tree, so a shader directory ships with every application that imports the library.

A consumer writes `huxerui.live2d = { git = "…", rev = "…" }` and `import huxerui.live2d;`.
Distribution is the source: a git revision today, an index entry when published.

## The SDK

```bash
git clone https://github.com/HuxerUI/HuxerUI && cd HuxerUI
mcpp build                                    # the framework, this host
mcpp test                                     # mcpp/huxerui-tests
mcpp build --target x86_64-linux-android      # any row
cd mcpp/examples/01-import && mcpp pack --target x86_64-linux-android --format apk
```

`mcpp/` holds the rule packages the framework and every application share: `huxerui-build-rules` (what to compile, hcg, hrc), `huxerui-build-rules-gtk` (the Linux payload table, declared once) and `huxerui-build-rules-dist` (the five formats, through `mcpp:plugins`).
CMake remains the other build system, untouched; CI's parity job checks that the two describe the same sources, and [`mcpp/README.md`](../../mcpp/README.md) says what to touch when adding a file or a platform.
